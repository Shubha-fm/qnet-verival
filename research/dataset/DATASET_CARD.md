# VeriQKD-Bench v1: synthetic coordination-model benchmark

## Nature and intended use

This dataset was generated by the included finite-state QKD coordination model. It is **synthetic, model-derived data**, not physical QKD measurements, deployment traffic, operator incident records, cryptographic key material, or an externally curated set of real software defects. It supports reproducibility, graph-checking experiments, property-sensitivity studies, and inspection of the provided abstraction.

## Coverage

The frozen grid has 522 distinct canonical configurations:

| Family | Configurations | Design |
|---|---:|---|
| Structural | 72 | 1--6 relays; failure and delay on/off; short, exact, slack budgets |
| Concurrency | 72 | Selected 2/3-session configurations; 0/1 relay; shared/separate candidate keys; atomic/split/reserved delivery; failure on/off; short/slack budget |
| First-order faults | 288 | 12 variants x 3 relay counts x 2 failure modes x 2 delay modes x 2 budgets |
| Localized faults | 22 | Selected session, hop, and relay locations |
| Combined faults | 56 | 28 selected operator pairs x 2 relay counts |
| Route lengths | 12 | 3 route-length menus x 2 failure modes x 2 delay modes |

After execution, 513 cases completed and nine reached the declared state cap. Capped records have null properties and no verification verdict. All complete graphs passed the C++ graph-algorithm cross-check. See `case_summary.csv` for exact outcomes. A configuration is not an independent real-world defect. Many configurations can have identical graph structure.

Additional records contain 30 random-testing scenarios, 120,000 seeded execution traces, and repeated performance experiments. These are separate experiment groups, not additional rows hidden in the 522-case grid. The generator scripts define their exact schedules and seed streams.

## File organization

- `design.json`: complete frozen ordered grid, family labels, tags, canonical configurations.
- `configurations/<case_id>.json`: one input per grid case.
- `outcomes/<case_id>.json`: complete or capped outcome, measured worker time/RSS, property map, witnesses where available.
- `graphs/<case_id>.graph.gz`: totalized graph for every completed case.
- `case_summary.csv`: flat comparison table; property values are pass/fail/unknown.
- `testing_scenarios.json`: thirty additional testing configurations.
- `random_traces.jsonl.gz`: one record per sampled execution trace.
- `SCHEMA.json`: structural JSON schema for grid outcomes.

## IDs and integrity

A case ID is the first sixteen hexadecimal digits of SHA-256 over the sorted compact JSON configuration. It includes the state cap, delivery mode, fault list, and fault targets. IDs identify configurations, not semantic graph-isomorphism classes. A graph checksum covers the exact compressed portable graph file, using a fixed gzip timestamp and no embedded filename. `MANIFEST.sha256` in the package records delivered file digests.

## Graph encoding

After decompression, the header is `number_of_states number_of_edges`. The next `number_of_states` lines contain `terminal_flag violation_mask`. The remaining lines contain integer `source target` edges. State zero is initial. Bits 0--8 correspond to P1--P9, with the P8 bit zero in vertex labels. The C++ checker independently determines P8 by searching for a reachable nonterminal cycle. Parallel action edges are retained; action text is not in this portable graph. Safety labels are supplied by the Python model exporter, so the C++ pass is not independent validation of safety-predicate meanings or transition generation.

## Trace schema

Each sampled trace contains `scenario_id`, `scheduler`, `seed`, `episode`, `actions`, `steps`, `violations`, `outcome`, and `loop_start`. Scheduler is `uniform` or `progress_biased`; seeds are 0--19. Each seed trial has 100 episodes. Uniform sampling selects uniformly among enabled **model actions**. The second scheduler weights LinkFailure by 0.02, expiry by 0.05, delay by 0.10, and other actions by 1. These weights encourage deeper service execution; they are not calibrated physical event probabilities.

`violations` lists properties with witnessed failures. A terminal-free repeated full state supports a P8 cycle witness; a nonterminal no-successor state supports a deadlock witness. A finite trace without such evidence does not prove liveness. The audit replays every recorded action and verifies that observed failures are among the exhaustive scenario failures.

## Generation and provenance

- Parameter design: deterministic Python source in `src/design.py`.
- Reference semantics and predicates: `src/model.py`.
- Exhaustive graph checker: Python BFS plus reverse AF fixed point.
- Independent graph-level check: C++ reachability, label aggregation, and Kahn cycle elimination.
- Tests: thirteen targeted tests plus a complete dataset witness/trace replay audit.
- Environment: exact Python, OS, CPU, and compiler records in `results/environment.json`.
- Source hashes and file manifest: included with the delivered package.

## Limitations and responsible interpretation

The model has no real quantum state, quantum channel noise, key bit values, cryptographic adversary, general packet queue, unbounded arrival process, replenishing inventory, source-code parser, or deployment-conformance relation. Route alternatives are hop counts, not physical network graphs. The reservation repair is a reference state-machine repair, not a patch applied to an external controller. No public benchmark ranking or clinical/security certification is implied.

The dataset has no personal information or real secret keys. It does not come with a fabricated repository address or DOI. An explicit public distribution license has not been selected; the manuscript's authors should choose one before an external archival release. A future learning-based use should split by configuration families and graph hashes to avoid leakage from duplicate or closely related model instances. This work does not train a machine-learning model or claim a held-out accuracy score.
